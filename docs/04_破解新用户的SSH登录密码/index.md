## 📖 第一部分：背景知识

### 一、SSH 协议原理详解

#### 1.1 什么是 SSH？

**SSH（Secure Shell，安全外壳协议）** 是一种加密的网络传输协议，主要用于在不安全的网络中为远程登录会话和其他网络服务提供安全通信。它的设计初衷是取代古老的 `telnet`、`rlogin`、`FTP`、`rsh` 等明文传输协议。

SSH 协议最初由 Tatu Ylönen 于 1995 年设计，目前主流版本为 **SSH-2**（SSH-1 因存在安全缺陷已被废弃）。

**SSH 的核心特性：**

```
┌──────────────────────────────────────────────┐
│              SSH 核心安全特性                 │
├──────────────────────────────────────────────┤
│  🔒 数据加密        传输内容加密，防窃听      │
│  🔑 数据完整性      防止数据被篡改            │
│  🪪 身份认证        确认连接双方身份          │
│  🔐 密钥交换       安全协商会话密钥          │
└──────────────────────────────────────────────┘
```

#### 1.2 SSH 协议分层架构

SSH 协议采用经典的 **客户端-服务器架构**，整体分为三层：

```
┌────────────────────────────────────────┐
│           SSH 协议分层架构               │
├────────────────────────────────────────┤
│  应用层    │ SSH 客户端 / SSH 服务器     │
│           │ (sftp, scp, ssh, etc.)      │
├────────────────────────────────────────┤
│  SSH 协议层 │ 认证协议 / 连接协议         │
│           │ (SSH Auth / SSH Conn)      │
├────────────────────────────────────────┤
│  传输层协议 │ 加密、压缩、完整性验证     │
│           │ (SSH Transport Layer)      │
├────────────────────────────────────────┤
│  传输层    │ TCP/IP (默认端口: 22)       │
└────────────────────────────────────────┘
```

**各层职责：**

- **传输层（SSH-Transport）**：负责加密、密钥交换、服务器认证，是整个协议的安全基石
- **认证协议（SSH-Auth）**：负责客户端身份认证，支持密码认证、公钥认证等多种方式
- **连接协议（SSH-Conn）**：在已认证的通道上复用多个逻辑通道（shell、端口转发、文件传输等）

#### 1.3 SSH 握手流程（连接建立过程）

SSH 连接建立分为以下几个阶段：

**第一步：协议版本协商**

```
客户端 ── TCP 三次握手 (端口 22) ──→ 服务器
客户端 ── "SSH-2.0-OpenSSH_8.9" ──→ 服务器
服务器 ── "SSH-2.0-OpenSSH_8.9" ──→ 客户端
```

**第二步：密钥交换（Diffie-Hellman）**

```
客户端 ←──→ 服务器
   │
   ├─ 交换算法协商 (encryption, MAC, key exchange, host key)
   │
   ├─ 客户端生成 E（DH 公钥参数）
   ├─ 服务器生成 F（DH 公钥参数）
   │
   ├─ 双方计算共享密钥 K
   ├─ 双方从 K 派出会话密钥 H
   │
   └─ 生成临时会话密钥用于对称加密
```

**第三步：用户认证**

```
客户端 ── SSH-USERAUTH 请求 ──→ 服务器
服务器 ── 认证挑战 ──→ 客户端
客户端 ── 认证响应 ──→ 服务器
        ↓
   认证成功 → 建立加密会话通道
   认证失败 → 重新尝试（有限次数）
```

#### 1.4 SSH 支持的加密算法

SSH 协议支持多种加密算法，以下是常见的分类：

**对称加密算法（Symmetric Encryption）：**

| 算法 | 密钥长度 | 说明 |
|------|---------|------|
| AES | 128/192/256 位 | 最常用，安全性高 |
| ChaCha20 | 256 位 | Google 推荐，适合移动设备 |
| 3DES | 168 位 | 老旧算法，不推荐使用 |
| AES-GCM | 128/256 位 | 支持认证加密（AEAD） |

**非对称加密算法（Asymmetric Encryption）：**

| 算法 | 用途 | 说明 |
|------|------|------|
| RSA | 密钥交换 + 签名 | 经典算法，建议 ≥2048 位 |
| ECDSA | 签名 | 曲线算法，性能好 |
| Ed25519 | 签名 | 现代算法，安全性高，推荐 |

**哈希算法：**

| 算法 | 用途 |
|------|------|
| SHA-256 / SHA-512 | 密钥交换完整性验证 |
| HMAC-SHA2 系列 | 消息认证码（MAC） |

#### 1.5 SSH 数据包结构

SSH 数据包以二进制格式传输，每个数据包结构如下：

```
┌────────────────────────────────────────────────┐
│              SSH 数据包结构                      │
├────────────────────────────────────────────────┤
│  字段           │ 长度      │ 说明              │
├────────────────────────────────────────────────┤
│  Length         │ 4 字节    │ 数据包总长度       │
│  Padding Length │ 1 字节    │ 填充数据长度       │
│  Payload        │ 变长      │ 实际载荷数据       │
│  Padding        │ 变长      │ 随机填充数据      │
│  MAC            │ 变长      │ 消息认证码         │
└────────────────────────────────────────────────┘
```

### 二、SSH 认证机制

SSH 支持多种用户认证方式，以下是主流的几种：

#### 2.1 密码认证（Password Authentication）

```
┌─────────────────────────────────────────────────────────┐
│             SSH 密码认证流程                            │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  用户 ──→ 输入密码 ──→ SSH 客户端                       │
│       │                                                │
│       │ 加密传输 (使用会话密钥)                         │
│       ↓                                                │
│  SSH 服务器 ←── 接收到加密的密码                       │
│       │                                                │
│       │ PAM (Pluggable Authentication Modules)          │
│       ↓                                                │
│  系统验证密码 ──→ /etc/shadow 比对                     │
│       │                                                │
│       ↓ (成功)              ↓ (失败)                   │
│  允许登录                 拒绝登录                    │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

**密码认证的特点：**
- ✅ 简单易用，无需额外配置
- ✅ 跨平台支持
- ❌ 密码易被暴力破解（尤其是弱密码）
- ❌ 密码传输依赖加密通道（中间人攻击风险）

#### 2.2 公钥认证（Public Key Authentication）

```
┌─────────────────────────────────────────────────────────┐
│             SSH 公钥认证流程                            │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  ① 用户生成密钥对                                       │
│     ssh-keygen -t ed25519                               │
│           │                                             │
│           ├── ~/.ssh/id_ed25519        (私钥，本地保存)  │
│           └── ~/.ssh/id_ed25519.pub    (公钥，上传到服务器)│
│                                                         │
│  ② 将公钥添加到服务器                                   │
│     cat ~/.ssh/id_ed25519.pub | ssh user@host           │
│     "mkdir -p ~/.ssh && chmod 700 ~/.ssh"              │
│                                                         │
│  ③ 登录时客户端证明身份                                 │
│     客户端 ──→ 发送用户名 + 公钥 ID ──→ 服务器          │
│     服务器 ←── 发送随机挑战 ←── 服务器                  │
│     客户端 ──→ 用私钥签名挑战 ──→ 服务器                │
│     服务器 ←── 验证签名 ←── 服务器                      │
│           │                                             │
│           ↓ (签名有效)                                  │
│     允许登录                                            │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

**公钥认证的安全性优势：**
- ✅ 无需在网络中传输密码
- ✅ 私钥永不离开本地
- ✅ 服务器可配置禁用密码认证（从根本上防御暴力破解）
- ✅ 支持将私钥加密存储（添加密码保护）

#### 2.3 其他认证方式

| 认证方式 | 说明 |
|---------|------|
| **Keyboard-Interactive** | 交互式认证，支持 OTP（一次性密码）等 |
| **Host-based** | 基于主机而非用户的认证（不推荐） |
| **GSSAPI** | 通用安全服务API，支持 Kerberos 等 |
| **PAM** | 通过 Linux PAM 模块扩展认证方式 |

### 三、SSH 暴力破解原理

#### 3.1 什么是暴力破解（Brute Force Attack）？

**暴力破解** 是指攻击者通过自动化工具，尝试大量可能的用户名/密码组合，直到找到正确凭证的攻击方式。对于 SSH 来说，暴力破解的目标是**绕过服务器的认证机制**。

```
┌──────────────────────────────────────────────────────────────┐
│                    SSH 暴力破解原理                           │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│   攻击者电脑 ──→ Hydra ──→ 目标 SSH 服务器                   │
│                      │                                       │
│                      │ 大规模并发请求                        │
│                      │ 逐个尝试密码组合                      │
│                      ↓                                       │
│              [password: admin123]  ✗ 失败                    │
│              [password: password]  ✗ 失败                   │
│              [password: 123456]    ✗ 失败                   │
│              [password: admin@2024] ✓ 成功！                 │
│                      │                                       │
│                      └──→ 获取目标服务器访问权限            │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

#### 3.2 Hydra 对 SSH 协议的处理方式

Hydra 是目前最强大的在线密码破解工具之一，由 THC（The Hacker's Choice）组织开发。对于 SSH 协议，Hydra 的工作方式如下：

**Hydra SSH 破解的工作流程：**

```
Step 1: 连接建立
        Hydra 连接到目标服务器的 22 端口
        发起 TCP 连接 → 完成 SSH 握手 → 建立加密通道

Step 2: 发起认证请求
        Hydra 构造 SSH-USERAUTH 请求包
        携带目标用户名（如 "root"）

Step 3: 等待服务器响应
        如果用户存在 → 服务器回应 "Authentications that can continue..."
        如果用户不存在 → 服务器可能断开连接或拒绝认证

Step 4: 尝试密码
        Hydra 使用字典中的每个密码构造认证请求
        发送加密的密码尝试
        等待认证结果

Step 5: 判断结果
        收到 "Authentication succeeded" → 找到密码，记录结果
        收到 "Authentication failed"   → 尝试下一个密码
        连接断开/超时                    → 重试或跳过
```

**Hydra 的技术细节：**

- Hydra 使用 `libssh` 或原生 SSH 库实现 SSH 协议通信
- 支持并发连接（`-t` 参数控制并发数）
- 支持暂停和恢复（通过 `-s` 和保存状态）
- 能够检测锁定账户（多次失败后账户被锁）

#### 3.3 暴力破解的效率因素

SSH 暴力破解的成功率和效率受多种因素影响：

| 因素 | 影响 |
|------|------|
| **密码强度** | 弱密码（123456, admin, password 等）破解率高 |
| **字典质量** | 高质量、自定义的字典比通用字典效果好得多 |
| **网络延迟** | 延迟越高，破解速度越慢 |
| **服务器性能** | 服务器 CPU 快，认证处理快，但日志量大 |
| **并发数量** | 并发数高破解快，但容易被检测和封锁 |
| **账户锁定策略** | 有账户锁定策略的服务器限制破解尝试次数 |
| **是否使用 Fail2Ban** | Fail2Ban 会封禁来源 IP，大幅限制破解效率 |

#### 3.4 暴力破解的变种

除了最基础的暴力破解，还有以下变种：

**① 凭证填充（Credential Stuffing）**

利用从其他平台泄露的用户名/密码组合，在多个网站上批量尝试（同一密码多平台使用）。

**② 字典攻击（Dictionary Attack）**

使用预定义的词汇列表（词典）替代纯随机字符组合，大大提高破解效率。

**③ 混合攻击（Hybrid Attack）**

在字典词的基础上进行规则化变形，如 `password` → `Password123`、`P@ssw0rd` 等。

**④ 社会工程学攻击**

利用目标个人信息（生日、姓名、宠物名、手机号）生成个性化字典。

### 四、常见防御手段

#### 4.1 密码层面的防御

| 防御手段 | 说明 | 效果 |
|---------|------|------|
| 强密码策略 | 要求大小写字母+数字+特殊字符，长度≥12位 | ⭐⭐⭐⭐⭐ |
| 禁止使用弱密码 | 通过 PAM 模块拒绝常见弱密码 | ⭐⭐⭐⭐ |
| 定期更换密码 | 每 90 天强制更换一次密码 | ⭐⭐⭐ |
| 禁止用户名作为密码 | 不允许用户密码与用户名相同 | ⭐⭐⭐ |

#### 4.2 账户层面的防御

| 防御手段 | 说明 | 效果 |
|---------|------|------|
| 账户锁定策略 | 连续 N 次失败后锁定账户 M 分钟 | ⭐⭐⭐⭐ |
| IP 白名单 | 仅允许特定 IP 连接 SSH | ⭐⭐⭐⭐⭐ |
| 双因素认证（2FA） | 密码+动态验证码双重验证 | ⭐⭐⭐⭐⭐ |
| 禁用 root 直接登录 | 必须通过普通用户提权 | ⭐⭐⭐⭐ |

#### 4.3 服务层面的防御

| 防御手段 | 说明 | 效果 |
|---------|------|------|
| 变更默认端口 | 将 SSH 从 22 端口改到其他端口 | ⭐⭐ |
| 限制并发连接数 | 防止大规模并发暴力破解 | ⭐⭐⭐ |
| Fail2Ban 自动封禁 | 检测暴力破解行为并封禁来源 IP | ⭐⭐⭐⭐ |
| 禁用密码认证 | 强制使用密钥认证 | ⭐⭐⭐⭐⭐ |
| 配置 AllowUsers / DenyUsers | 白名单/黑名单控制允许登录的用户 | ⭐⭐⭐⭐ |

```
VirtualBox 主界面 → 点击"新建(N)"按钮
```

填写以下配置信息：

| 配置项 | 值 |
|--------|-----|
| **名称** | SSH-Target |
| **文件夹** | 自定义（建议 D:\VMs） |
